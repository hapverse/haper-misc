# Print-on-demand: security audit (r1)

Auditor: navjot-security. Date: 2026-10-12. Scope: the UNCOMMITTED print feature in haper-backend, plus the haper-admin Print Queue. This was a read-only audit, checked by reading the code and running two small local in-memory probes.

## Verdict

**NOT READY to enable on any store.** There are 2 HIGH findings. Both let any logged-in customer take the customer API down. There are also 4 MEDIUM findings.

The core design is solid:
- Every route is scoped to the owner (customer side) or the store (admin side).
- An audit row is written before any staff download link is issued, and no link is issued if that write fails.
- S3 keys are generated by the server.
- Uploads are rebuilt into a clean A4 PDF.
- Checkout claims each job inside a transaction, and the wallet write is guarded.
- The purge cannot delete another user's file.

Counts: CRITICAL 0, HIGH 2, MEDIUM 4, LOW 8.

---

## HIGH

### H1. A hostile PDF can exhaust memory and CPU on the customer API (confirmed)
- **Location:** `packages/shared/utils/print-normalise.utils.js:95,103,145`. It is called in-process from `packages/user/src/routes/print/controller.js:94`.
- **What can go wrong:** The rebuild step fully expands every page's compressed content into memory. There is no size cap, no time limit, and no isolation. The expansion runs synchronously, so it also freezes the Node event loop while it works.
- **Evidence:** A local probe of `normalise()` showed that a small upload (tens of KB) drove the process to more than 1 GB of memory and blocked it for several seconds. A full 20 MB upload is far beyond that. All other customer requests stall, and the process can be killed by running out of memory. The limits that exist (20 MB file size, 200 pages, 20 uploads/hour per user) do not bound the *expanded* size. Many accounts can be used at once.
- **Fix:**
  - (a) Run `normalise` in a `worker_threads` Worker (or a child process). Set `resourceLimits` (for example `maxOldGenerationSizeMb: 512`) and a wall-clock timeout (for example 20 s) that terminates the worker. On a kill, return 422 "file could not be processed".
  - (b) Cap concurrency with a process-wide semaphore (for example 2 normalisations at once); return 503 when it is busy.
  - (c) Optional: put a budget on total expanded content before embedding.

### H2. multer 1.4.5-lts.1 (known DoS/crash CVEs) is now reachable by every customer
- **Location:** `packages/user/src/routes/print/middleware.js:61-82`. `package-lock.json` pins `node_modules/multer` at 1.4.5-lts.1.
- **What can go wrong:** CVE-2025-7338 and CVE-2025-47944 (affects >=1.4.4-lts.1 and <2.0.2) let a malformed multipart request crash the process. CVE-2025-47935 is a memory leak. Until now multer was only used behind admin/delivery logins. This route opens it to any customer account. The local `npm audit` database did not flag it; the public advisories (GitLab advisory DB, Express security release of 2025-07-31) do.
- **Fix:** Upgrade to `multer@^2.0.2`. It is a drop-in replacement for `memoryStorage` + `limits`. Re-run the print-upload and delivery-profile tests afterwards.

## MEDIUM

### M1. `print.manage` alone can cancel and refund an order, bypassing `orders.change_status` (confirmed)
- **Location:** `packages/admin/src/routes/print/router.js:19`. `controller.js:98-124` (`cancelThroughOrderFlow` calls `markOrderAdmin` directly). `:280`.
- **Evidence:** In an in-memory probe, a manager holding only `print.view` + `print.manage` got **403** from `PATCH /admin/order/mark-status-admin`. The same manager rejected the job and got **200**: the order became ADMIN_CANCELED and ₹50 was refunded. A SUPPORT user granted `print.manage` from the Team page can do the same. SUPPORT is listed in `storeRoles` even though the support preset leaves print out.
- **Impact:** Revoking cancel/refund rights from someone does not stop them cancelling and refunding print orders.
- **Fix:** On the reject route, also require `P.ORDERS.CHANGE_STATUS`, or check `checkPermission(req.admin, ORDERS.CHANGE_STATUS)` inside `rejectJob`. Separately, decide whether SUPPORT belongs in `storeRoles`. If support is meant to be excluded, remove `R.SUPPORT` from print routes.

### M2. The customer's file name (PII) is copied onto the order and outlives the file
- **Location:** `packages/user/src/routes/print/checkout.controller.js:176` writes `items[].print.fileName` onto the order.
- **Impact:**
  - **Riders and support can see it.** `getDeliveryDetail` (`shared/repositories/order.repository.js` ~485, projection only drops `__v`/`codConversion`) returns full items, so riders see names like "Aadhaar_Rahul_Kumar.pdf". Admin order endpoints return it to anyone with `orders.view` (support included), who lacks `print.view`.
  - **It is never deleted.** Purge deletes the file but keeps `print-jobs.file.originalName`, `file.sha256` (a fingerprint of the original document) and the order copy. Account deletion (`expireUserJobs`, `account-purge`) does not scrub them either.
- **Fix:** Don't store the file name on the order. Read it from the print job only where `print.view` applies, and project it out of the delivery and generic admin order reads. At purge time, set `file.originalName = "document"` and `file.sha256 = null`. Apply the same scrub on account anonymisation.

### M3. Purge can silently never run, and the "backstop" is undefined
- **Location:** `packages/cron/src/jobs/print-file-purge.js:93-96` (`isConfigured()` false means `console.log` + return). `:126-127` (overdue alert is only a log line).
- **Impact:** If `PRINT_S3_BUCKET` is set on the user API but missing in the cron env, uploads keep landing and nothing ever deletes them. Nobody is alerted. The 24-hour privacy promise breaks quietly.
- **Mismatch:** The plan proposes a 7-day lifecycle backstop (plan 7b #14), but the code keeps files of ordered jobs for up to 14 days (`ORDERED_CEILING_MS`, checkout.controller.js:15). A 7-day rule would delete files for slow or UN_DELIVERED orders. A rule longer than 14 days is the only safe backstop.
- **Fix:**
  - Log at error level / alert when the bucket is unset in cron.
  - Fail the boot health check if print is enabled on any store and the cron has no bucket.
  - Send the overdue count to a real alert channel.
  - Set the lifecycle rule to 15 days (see checklist), or lower the ceiling to match the lifecycle.

### M4. sharp 0.33.4 has open HIGH advisories and now processes untrusted customer images
- **Location:** `print-normalise.utils.js:47`. Root `package.json` has `sharp ^0.33.4`.
- **Evidence:** `npm audit`: GHSA-f88m-g3jw-g9cj (libvips CVEs, <0.35.0), GHSA-rgj7-g3m4-5g8c (libheif), GHSA-wq5f-xc86-pv6w (librsvg). The magic-byte check limits input to JPEG/PNG, so the HEIF and SVG paths cannot be reached. Whether the libvips CVEs hit the JPEG/PNG paths was not verified.
- **Fix:** Upgrade to `sharp@>=0.35.5`. Keep `limitInputPixels` as it is. Run the image path inside the H1 worker as well.

## LOW

- **L1.** Nothing checks that `PRINT_S3_BUCKET` differs from the public catalogue bucket (`AWS_S3_BUCKET_NAME`, which is served by the CDN). If set to the same value by mistake, ID documents land on public, guessable-ish keys. Fix: at boot, assert the two names differ in `print-s3.utils.js:13-20`.
- **L2.** The rate limit fails open when Redis is down (`middleware.js:33-40`). The fallback cap of 20 drafts can be bypassed by deleting drafts, because a deleted draft becomes EXPIRED and no longer counts. Fix: also count uploads in the last hour from Mongo (`createdAt`).
- **L3.** Each abandoned payment pushes `purgeAfter` out another 24 h (`print-job.repository.js:403`). An order-then-abandon loop keeps a file alive with no end date. `orderPurgeAt` keys on `updatedAt`, which moves whenever the order is touched (`print-file-purge.js:45`). Fix: carry the original upload time and cap total draft life (for example 72 h from upload). Use a fixed status-change timestamp.
- **L4.** Print price-config changes are audited best-effort, after the write (`admin/.../print/controller.js:353`). A failed audit leaves a money change with no record. Fix: use `auditUtils.logAtomic` inside a session, or `logCritical` before responding.
- **L5.** 5xx messages are only masked when `NODE_ENV=production` (`user/src/middleware/error.js:57`). In dev, raw AWS errors (bucket/role ARN) and repository `error.message` reach the client. Fix: mask unless the env is local/test.
- **L6.** Customer responses that carry `previewUrl` (`print/controller.js:125,140`) do not send `Cache-Control: no-store`, while the admin download does. Fix: add the header.
- **L7.** `@aws-sdk/*` 3.600 pulls in `fast-xml-parser` (critical/high advisories). It only parses S3 responses, so it is not reachable with attacker data. Fix: upgrade the SDK and `s3-request-presigner` to `>=3.894`.
- **L8.** The consent record does not bind the text version the client actually showed: the client sends only `consent=true` and the server stamps a constant (`controller.js:11,89,119`). IP and user agent are not stored. Fix: require `consentVersion` from the client, reject a mismatch, and store IP/UA.

## Checked and found OK (no finding)
- **IDOR:**
  - Every customer route filters on `userId`.
  - Admin routes check `assertStoreAccess`; another store's job returns 404, as tested.
  - A super-admin is global by design, and `x-store-id` cannot widen a store role.
  - Warehouse roles are blocked by `requireRole`.
- **Path/key injection and SSRF:** keys are `print/<userId>/<new ObjectId>.pdf`, never built from user input. There is no URL fetching anywhere in the feature.
- **File-name XSS:** `sanitizeFileName` keeps only letters, numbers, space and `._()-`, which strips `<>"'`, control and bidi characters. The admin UI renders it as React text. Email uses the server-built line name.
- **Rebuilt PDF:** annotations, forms, attachments and page actions are not carried over.
- **Content-Disposition:** set by the server from the order id. The preview is inline on the S3 origin.
- **Signed URLs:** 5-min staff TTL and 10-min customer TTL. Every staff download writes a fail-closed audit row before the link exists. The response is `no-store`. URLs are not logged.
- **Money:**
  - The server recomputes the price, and `expectedTotal` is only compared.
  - copies is a strict integer from 1 to 50.
  - Page ranges are parsed strictly with a bounded length.
  - Billable sides are capped.
  - Amounts are kept in integer paise.
  - Wallet is whole rupees, and any Razorpay remainder is at least ₹1.
  - `deductWallet` is guarded by `coins >= amount`.
  - The job claim inside the transaction stops double ordering. A paid or rejected job cannot be ordered again. A late capture after release goes to the wallet.
- **Order guards:** edit, convert-to-COD and reopen all refuse print orders. Supersede skips them.
- **Purge:** the claim is guarded, a key that is already missing counts as success, and rows stuck in PURGING are retried.

## S3 bucket checklist (for the human creating it)
1. Create a **new dedicated bucket** (for example `haper-print-docs-<env>`) in `ap-south-1`. Use one bucket per environment. It must **not** be the catalogue bucket, and it must **not** sit behind CloudFront or the CDN.
2. **Block Public Access:** turn on all 4 settings, on the bucket and at the account level.
3. **Object Ownership:** Bucket owner enforced (this disables ACLs).
4. **Versioning:** leave it **never enabled**. Once enabled it can only be "suspended", and deleted files then survive as old versions. If it was ever turned on, add a lifecycle rule that expires noncurrent versions after 1 day and removes expired delete markers.
5. **Default encryption:** SSE-S3 (AES256), with a bucket policy that denies `PutObject` unless `s3:x-amz-server-side-encryption = AES256`. If you choose SSE-KMS instead, the backend role also needs `kms:Decrypt`/`GenerateDataKey`.
6. **Bucket policy:** deny any request where `aws:SecureTransport = false`.
7. **Lifecycle rule** on prefix `print/`: expire current objects after **15 days** (just over the 14-day ordered ceiling). Add abort-incomplete-multipart after 1 day.
8. **IAM** for the backend instance role(s) only, scoped to `arn:aws:s3:::<bucket>/print/*`. Grant `s3:PutObject`, `s3:GetObject` and `s3:DeleteObject` only. Do not grant `s3:ListBucket`, `s3:*` or bucket-level admin. Give the cron role only `s3:DeleteObject`, plus `GetObject` if needed. Do not grant the static `AWS_S3_ACCESS_KEY_ID` user access to this bucket.
9. **Logging:** turn on server access logs or CloudTrail data events, written to a separate log bucket with short retention. They must not land in the print bucket.
10. No CORS configuration is needed, because downloads are top-level navigations. Leave CORS empty.
11. Set `PRINT_S3_BUCKET` in **both** the user API and cron environments (see M3). Then confirm the cron's first run logs `candidates=` and not "not set".
