# Verify Bill: Add item + Edit line

## Status (update this line as phases land)
Approved by user 2026-08-09. Build in progress: Phase 0 (invoice case-sensitivity fix) + Phase 1 (Edit line UI) started 2026-08-09. Phase 2 (receipt identity schema field) + Phase 3 (Add item UI) not yet started — blocked on Phase 0/1 landing first (approved sequencing). Phase 4 (MRP inline editing) deferred, not scheduled.

## Goal
A warehouse clerk who has already entered a supplier bill and then spots a missed item should be able to add that item to the same bill from the Verify Bill screen (`haper-admin`, route `/warehouse/verify-bill`), without retyping the invoice number. A warehouse manager should additionally be able to correct a wrong quantity, cost, expiry, or batch code on a line of that bill from the same screen, with an unmissable warning when the correction touches more stock than just that one delivery (a "lot" can be fed by multiple invoices pooled together).

Real motivating example: on 06 Aug 2026, invoice **TS6826** was entered with 18 items. On 09 Aug a 19th item was found on the paper bill. The clerk went to Receive Goods, retyped the invoice number as lowercase "ts6826" (a typo), got no duplicate warning (case-sensitivity bug — see Phase 0), and ended up creating a second, disconnected 1-item "bill" instead of appending to the original. Confirmed live in production data via a local read-only DB dump.

## The core design decision: how an appended line joins its original bill
"Which rows belong to the same bill" is not stored — it's derived at read time by grouping rows sharing `{refLabel, supplierId}` within a 5-second `createdAt` window. An append days later falls outside that window and would fork into a second bill. Approved fix: add ONE new nullable field to `stock-movements.schema.js`:
```
receiptAt: { type: Date, default: null }
```
Fresh receives stamp every line `receiptAt = floor(now/5000)*5000` (identical to today's fallback bucket, so new rows group exactly as before). Appends read a sibling row's `receiptAt` (or its fallback) and stamp the new line with that value, joining the original bill permanently. All grouping reads switch to `receiptAt ?? floor(createdAt/5000)*5000` — every pre-existing row (null receiptAt) falls through to today's identical fallback, so historical bills are completely unaffected. No backfill, no migration script needed.

## Approved answers to the open questions (Q1-Q8)
- **Q1 (append semantics):** Approved — the `receiptAt` field approach above (not the cheaper "just group by invoice number, merging all historical repeats" alternative, which would incorrectly merge genuine duplicate double-entries too).
- **Q2 (MRP editing):** Deferred to a fast-follow (Phase 4, not scheduled). MRP lives only on the per-line ledger snapshot, not on lot-level records, so it needs its own small endpoint/modal, not a field bolted onto `CorrectReceiptModal`.
- **Q3 (permission split):** Confirmed — staff (`warehouse.receive_goods`) sees "Add item" only; managers/super-admins (`warehouse.manage`, which implies receive_goods) see "Add item" + "Edit" + "Change supplier". Controls are HIDDEN (not disabled) for users without permission, matching this page's existing convention. Staff-only users get a small caption noting they can ask a manager.
- **Q4 (after an Edit, the bill line's numbers don't visibly change):** Approved v1 approach — this is INTENTIONAL, not a bug (the ledger is append-only; a correction never rewrites the original receipt line, it adjusts live stock separately). Ship a session-only inline note under the corrected line explaining this ("Stock for lot X was corrected just now. This bill line still shows what was originally entered — that's the audit record."). A backend enhancement to make this note survive a page reload is a deferred fast-follow, not v1.
- **Q5 (the already-split TS6826/ts6826 bills in production):** Leave as-is for now. The case fix (Phase 0) prevents NEW splits; it does not retroactively heal this specific pair. A one-off prod data fix is a separate, deliberate, user-driven decision for later if wanted.
- **Q6 (interstitial copy):** Approved — the pooled-lot warning interstitial should spell out the arithmetic explicitly (e.g. "To change this invoice's 40 units to 45, set the lot's total to 101"), computed from real fetched numbers, not a hardcoded example.
- **Q7 (phasing):** Approved — ship in 2 stages: Phase 0 (case-sensitivity fix, backend-only) + Phase 1 (Edit line, frontend-only, zero backend risk) FIRST; then Phase 2 (receipt identity schema field, backend) + Phase 3 (Add item, frontend) SECOND, once Phase 0/1 have landed.
- **Q8 (accessibility):** Approved — fix the WCAG AA contrast failure found in warning banners (amber text on this theme measures below AA contrast) as part of this work: warning MESSAGE TEXT must render in `var(--text-primary)`, amber reserved for icon/border/tint only. Applies to the new Edit-line interstitial at minimum; fixing the same pre-existing pattern in `CorrectReceiptModal` and the Receive Goods duplicate-invoice banner is optional/bonus, not required.

## Phased build order
- **Phase 0** (backend, standalone, revertible): fix case-insensitive invoice-number matching in `findReceiptRowsByInvoice` (stock-movement.repository.js) — dedupe/lookup queries become case-insensitive; stored data keeps original casing; display-grouping (`groupReceiptRows`, `listReceipts` aggregation) intentionally left untouched until Phase 2 (coupled to the receiptAt work). New test file `procurement-invoice-case.test.js`.
- **Phase 1** (frontend only, zero backend change): extract a shared `computePooledCount` helper into `receipt.ts`; build new `EditLineContextModal.tsx` (the pooled-lot comparison interstitial, shown only when a lot was fed by >1 delivery); wire a manager-only "Edit" (pencil) action into `VerifyBillPage.tsx`'s line table, fetching live stock/batch/movement data on click (3 parallel calls) and opening `CorrectReceiptModal.tsx` (reused unmodified, reached via the interstitial when needed).
- **Phase 2** (backend): add `receiptAt` field to the schema; stamp it on fresh receives; switch `groupReceiptRows` + `listReceipts`'s aggregation to `receiptAt ?? floor(createdAt/5000)*5000`; add an `appendToReceivedAt` optional field to the `POST /receive` request contract so a client can explicitly say "this line belongs to that existing bill"; update the supplier-correction lookup to key off the same receipt identity so an appended line can't be left behind on the old supplier after a correction.
- **Phase 3** (frontend): extract the existing "Receive Goods" modal out of `WarehousesPage.tsx` into its own reusable file (pure move, no behavior change); add a locked/append mode (supplier + invoice number pre-filled and disabled, calm "adding to existing bill" strip instead of the alarming duplicate warning, submits with `appendToReceivedAt` set, no 409-confirm dance); wire an "Add item" button into Verify Bill's accordion header (visible to anyone with `receive_goods`).
- **Phase 4** (deferred): MRP per-line editing, new small endpoint + modal.

## Known risks / things to watch
- After an Edit, the bill's displayed qty/cost/mrp do NOT change (by design, append-only ledger) — this WILL look like a bug to someone who doesn't know it's intentional; the inline note (Q4) is the mitigation, make sure it's not accidentally dropped during implementation.
- Rolling back Phase 2 after it ships would make already-appended lines visually detach again (revert to looking like 2 separate bills) — no data loss, but is the one asymmetry of this approach worth remembering if a rollback is ever needed.
- The existing TS6826/ts6826 split in production is NOT healed by any of this work (Q5) — don't let anyone assume it silently fixes itself.
